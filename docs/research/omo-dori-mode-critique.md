# [재검토/비판적 감사] omo-dori-mode, 지금 omon-gateway에 정말 유효한 벤치마크인가?

> **일자**: 2026-10-08  
> **검토 결론**: **"90%는 우리가 이미 고통을 겪고 폐기/탈출한 과거(레거시) 방식의 재포장이며, 그대로 가져오면 게이트웨이가 다시 망가진다. 다만 단 1가지 원칙(Done 검증 프로토콜)만 선별 수용해야 한다."**

---

## 1. 뼈아픈 현실 대조: dori-mode의 본체는 무엇인가?

`omo-dori-mode` 코드를 깊이 파헤쳐보면 충격적인 사실이 드러납니다:
- **dori-mode는 새로운 시스템이 아니라, 과거 `OMOMEOW-MODE.md` 및 `agent-messenger`의 TypeScript 구현체**입니다.
- 실제로 코드베이스 전체가 `herdr` CLI를 서브프로세스로 때리고, 터미널 화면을 `screen tail`로 긁어 정규표현식(`[REPORT]`, `deadPanePatterns`)으로 감시하는 **TypeScript 기반 스크립트 모음**입니다.
- 즉, **우리가 바로 어제/오늘 수십 번의 실패를 겪고 `ai.omomeow.herdr` launchd 데몬을 완전히 죽이고(bootout/disable), 오모냥 코드를 Rust 네이티브 게이트웨이(`omon-gateway`)로 통합 마이그레이션한 바로 그 구형 아키텍처**와 완전히 동일합니다.

---

## 2. 왜 그대로 도입하면 안 되는가? (치명적 충돌 4가지)

### ① Herdr 터미널 스크래핑 의존성 (역행)
- **dori-mode 방식**: 터미널 GUI 가상화 도구인 `herdr`를 깔고, `herdr tab new`, `herdr pane read`로 텍스트 화면을 긁어서 상태를 파악.
- **우리가 겪었던 문제**:
  - `herdr` 프로세스가 백그라운드에서 죽거나(Zombie), 소켓이 끊기면 감시 데몬 전체가 먹통(`Hang`).
  - 터미널 버퍼 스크린을 긁는 방식은 ANSI 색상 코드, 줄바꿈 깨짐, 에이전트 도구 로그 노출로 인해 끊임없이 에러가 발생했음.
- **현재 우리의 방향**: Rust 게이트웨이가 OMO 데몬(`ws://127.0.0.1:19742`)과 **구조화된 JSON-RPC 프로토콜**로 직접 통신하는 것이 100배 안정적임. 여기에 다시 herdr 탭을 씌우는 것은 명백한 퇴행.

### ② "침묵과 답답함" 문제의 재발
- dori-mode는 레인(작업)을 띄우고 나면 **기본 15분(`nudgeAfterMin: 15`), 20분(`postAfterMin: 20`) 동안 아무 말도 하지 않고 기다립니다**.
- 대표님께서 오늘 말씀하신 핵심 피드백:
  > *"뭐 하나 시키면 아무반응없이 몇시간 기다려야되니가 너무 답답함. 일단 현재상황부터 빠르게 보고하고 작업해라."*
- dori-mode의 15~20분 침묵 루프는 대표님이 가장 답답해하시는 바로 그 패턴을 시스템적으로 강제하는 방식입니다.

### ③ Discord 토큰 및 세션 멀티플렉싱 파괴 위험
- dori-mode는 단일 사용자 전용의 1:1 메신저 봇 스크립트로 짜여 있습니다.
- 반면 `omon-gateway`는 다중 채널/스레드 고유 세션 바인딩, SQLite 기반 영속 트랜잭션, 크론 14종 스케줄러, Developer ID 코드사인을 갖춘 **엔터프라이즈급 멀티플렉서 데몬**입니다. dori-mode의 단발성 TS 스크립트는 이 구조를 감당하지 못합니다.

### ④ 불필요한 복잡도 (TypeScript + Bun + Rust 이중 데몬화)
- 게이트웨이(Rust) 외부에 또다시 Bun/TS 기반의 dori CLI 데몬을 띄우면, 프로세스 간 동기화 문제와 좀비 프로세스 관리 부담만 두 배로 늘어납니다.

---

## 3. 그렇다면, 진짜로 건질 수 있는 "유효한 알맹이"는 무엇인가?

dori-mode의 구조(Herdr, TS 스크립트, 느린 폴링)는 버려야 하지만, **소프트웨어 엔지니어링 철학 1가지는 매우 유효**합니다:

### 🌟 유효한 핵심: 「The Done Protocol (기계적 완료 검증)」
- **문제점**: 에이전트에게 일을 시키면 코드 한 줄 대충 고쳐놓고 "다 고쳤습니다!"라고 말로만 얼버무리는 현상.
- **dori-mode의 훌륭한 해결책**:
  - 에이전트의 말을 믿지 않고, 사용자가 지정한(또는 프롬프트에 정의된) **기계적 신호(Signal)**를 외부에서 강제로 실행하여 통과했을 때만 승인하는 것.
  - 예: `git diff` 확인, `cargo test` exit code 0 확인, `curl` 200 OK 확인.

---

## 4. 최종 결론 및 현실적인 벤치마킹 액션 아이템

`omo-dori-mode` 리포지토리를 통째로 시스템에 넣으려고 하거나, herdr/TS 스크립트를 가져오는 것은 **절대 해서는 안 되는 헛수고이자 퇴행**입니다.

대신 **아래의 경량화된 방식으로만 흡수**해야 합니다:

1. **외부 도구/패키지 추가 금지**: `herdr`, `dori CLI` 등 추가 설치 일체 배제.
2. **Rust 게이트웨이 내 "Done 검증 게이트"만 필요 시 내장**:
   - 디스코드 세션에서 장기 작업을 마칠 때, 백엔드 단에서 `cargo test`나 빌드 결과가 성공했는지 체크하는 간결한 밸리데이터 로직만 수용.
3. **즉각적 피드백 원칙 고수 (dori-mode의 15분 대기 거부)**:
   - 작업 시작 시 1초 내 즉각 상황 보고 -> 30초~1분 단위 하트비트/타이핑 유지 -> 완료 시 기계적 증거와 함께 보고.
