### Required lifecycle error ordering

For ordinary close, re-read verified_done and generation under lane serialization; cancel the actual backend token and observe task completion; call set_status(Done), archive, and non-force removal of explicitly owned worktrees from a surviving repository control cwd; only then commit closed. A failed Git remove retains verified_done and writes one close_failed containing useful Git stderr, scrubbed for gateway event delivery. A DiscordThreadError must propagate into a durable visible failure, not be logged away before closed. Partial external success needs a persisted receipt/reconciliation boundary for restart, including a missing-path/registration mismatch decision; blindly retrying removal can delete a replacement owner path. Forced close has explicit forced history and never upgrades to verified_done or weakens Git protection. The plan does not specify the forced-close failure state's exact representation; keep it unresolved rather than fabricate a verified state.

Owner reply uses durable message identity and the same serialized boundary. On verified_done, complete safe close first; on closed, reopen using the existing transaction/session reuse. Restore Working/unarchive before service admits a new turn. Preserve exact owner text and retain intent on failure. Existing `thread_owner` in the adapter is the engaged bot ID, not the human author; paired users/roles/allow-all are admission, not authority to reopen an owner's lane.
