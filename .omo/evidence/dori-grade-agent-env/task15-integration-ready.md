## Decisions proposed to the lead

1. **Cleanup is capability-based.** Only a path explicitly created or registered as lane-owned by an authorized CLI operation has removal authority. No cwd containment, creation time, transcript, brief or worktree-list result grants that authority. Current `cli::start` (`W/src/lanes/cli.rs:324-413`) only canonicalizes external cwd; it creates no worktree. Such lanes have an empty capability set: close skips removals and records `skipped_no_owned_worktrees`, truthfully, while still cancelling/joining, renaming/archiving and committing closed. Do not claim any external cwd was removed.
2. **A narrow registration interface only if task 15's removal acceptance is retained.** Proposed `lane register-worktree <key> --repo <surviving-control-cwd> --path <linked-worktree>` is explicit delegation of deletion authority, not discovery or creation. The caller must be authorized under the local CLI control boundary. Verify actual linked registration/common repository identity, reject main worktree, lane cwd and control cwd, then persist the capability. Synthetic registered owned paths prove removal. No worktree create/list/branch manager, automatic adoption, or arbitrary path deletion API. If the lead defers this interface, empty-capability close can ship narrowly, but removal acceptance remains unproven/deferred and must not be claimed complete.
3. **Durable intents, service-only effects.** CLI and adapter persist intents plus wake hints; the gateway lane service owns cancellation/join, thread effects, cleanup and final status. Accepted intent is not closed success. Ordinary failures preserve verified_done; forced failures preserve the captured original status, never fabricate verified_done. Retry requires an explicit request or startup reconciliation of an interrupted operation, not periodic destructive retries.
4. **Owner identity needs an explicit config decision.** W `main.rs:105-115` loads DISCORD_ALLOWED_USERS, DISCORD_ALLOWED_ROLES and DISCORD_ALLOW_ALL_USERS; source search found no owner-specific setting. These are admission controls, not owner authority. Recommended minimal policy: a dedicated DISCORD_LANE_OWNER_ID supplied through existing configuration, also subject to existing channel/user admission; no .env edits here or during implementation. An alternative requiring no new setting is singleton DISCORD_ALLOWED_USERS only, with reopening disabled if empty/multiple; adopting it is an explicit owner-policy decision, not an inference. Never grant owner authority to roles, pairing, allow-all or all humans. Do not hardcode the historical owner ID from plan prose.
5. **One lane per non-null Discord thread.** Add a partial unique index after a read-only duplicate probe on the authorized scratch/pre-migration database. Existing duplicates block migration with identities reported; never choose one, clear rows or silently rewrite ownership. Authoritative bot/thread identity must be persisted when thread creation returns; old unbound lane threads require explicit backfill evidence or remain ineligible for automatic owner reopen.

## Service ordering and CAS boundary

1. On normal close enqueue, require verified_done and capture reopen generation transactionally. Preserve existing force/note validation and legal forced transition history, but defer status/history close completion until effects finish. Return intent ID and pending status, not `status: closed`. A pending/running intent blocks new turns for that lane, including the ordinary working/not_done startup scan.
2. The single lane service claims pending -> running by CAS under per-lane serialization. Active bookkeeping must retain child cancellation token and joined completion identity. Cancel the actual run_cancelable token, wait for task/backend completion, then advance phase. Generation/status mismatch invalidates the attempt before effects; do not bypass the current capture/outcome/inbox generation fences.
3. When a thread is present, invoke real typed set_status(Done), then archive. Only advance after each succeeds. No sink means failure for a thread-bound lane, not successful no-op; threadless headless lanes record not-applicable and need no token. Typed Discord failures are durable visible failures, not swallowed logs. Use a required lifecycle transport trait/seam with no successful defaults; production delegates to existing DiscordThreads.
4. Remove only registered auxiliary capabilities, from the surviving control repo, argv `git -C <repo> worktree remove <path>`. No --force, branch deletion or recursive filesystem deletion. Revalidate repository/registration identity before setting removing and invoking Git. Successful removal stores removed. On refusal, retain verified_done for ordinary close, mark intent failed and insert one scrubbed close_failed event per attempt in the same transaction. A retry increments attempt; duplicate requests do not produce duplicate failure receipts.
5. Commit closed with existing legal forced history or verified_done -> closed history only after completed effects and final generation/status CAS. Clear task admission block only when no runnable lifecycle intent remains. close_failed is currently non-critical in dispatch; retain the existing judged policy unless the lead explicitly selects guaranteed admission. Do not silently alter Task 14 routing.

### Interrupted operations and retries

At service startup after socket ownership, reconstruct pending/running intents and enqueue missing verified_done intents once per generation. Task 13 returns newly verified keys only; recovery must also enumerate already verified rows without rerunning signals. Prior completed/failed rows are not blindly repeated; failed rows await an explicit retry.

After a crash during rename/archive, the same bot/thread generation can repeat the idempotent target-state edit or GET/reconcile it before advancing. Persisted owner reply prevents a concurrent unarchive while the service completes close. After a crash with a capability in removing, inspect the surviving repo's registered worktrees and exact path identity: both old registration and path absent permit recording removed; matching original registration permits non-force retry; replacement path/registration, mismatched identity, or ambiguous absence fails visibly without deletion. CAS cannot make external effects atomic; these explicit reconciliation rules supply the missing crash boundary. Process-local locks alone do not supply restart durability.

## Owner reply admission and exactly-once application

Intercept before adapter chat conversion/context/reactions/auto-thread/steer/debounce. Reuse message-type, webhook/self/bot, channel metadata and author admission checks, but do not require chat mention/activity gating for an authenticated owner lane thread. Match unique thread and persisted bot ID, then check the chosen actual owner config. Receipted lane traffic is consumed on duplicate, CAS loss and lifecycle failure, never routed to chat as recovery. A repeated delivery after status becomes working still finds its receipt before any chat path.

For verified_done, persist reply and schedule safe close first. Failed close leaves reply pending/failed-visible; it does not lose text or reopen directly from verified_done. For closed, serialize with close completion, cancel/join any old task, set Working thread status and unarchive while the DB lane stays closed (runner cannot start it); then one transaction performs existing closed -> working reopen/reset/history and inserts the exact first-prompt inbox entry with receipt applied/history ID. Crash before that transaction repeats idempotent thread restoration, not reopen history. Never mark applied before the reopen/inbox transaction commits. Existing reopen session reuse/fallback and generation fencing remain authoritative.

Distinct messages queued during the same reopen are not discarded: first receipt creates the reopened generation; later receipts for that original closed generation become exact lane inbox messages once each, with no second reopen history. Manual CLI reopen must use the same service ordering, rather than racing through the current direct transaction while archive is outstanding. Attachments and /stop require lead selection: this minimal increment supports ordinary text first-prompt reopening; unsupported lane controls must be consumed with visible failure, not quietly lost or sent to chat. No attachment hydration subsystem is added here.
