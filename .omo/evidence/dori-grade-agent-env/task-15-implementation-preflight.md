## Result and unresolved contracts

The dependencies expose the required state, resume, settlement and Discord operations, but there is no complete close coordinator. The smallest coherent implementation belongs to the existing lane service, not the CLI process. Three contracts must be resolved before destructive cleanup or automatic owner reopening can be called correct:

1. **Deletion ownership is absent.** `Lane` has `cwd`, not an owned-worktree manifest (`src/storage/lanes.rs:9-34`); migration `0031_lanes.sql:1-25` likewise records no creator, repository control directory or cleanup permission. `cli::start` canonicalizes a supplied/default cwd and inserts it; it creates no git worktree (`src/lanes/cli.rs:324-413`). Therefore neither the main lane cwd nor any other worktree is authorized for removal merely by being in this row.
2. **Owner identity is not the admission allowlist.** The inbound filter permits paired users, users, roles and allow-all (`src/discord/adapter.rs:1591-1623`). `DISCORD_ALLOWED_USERS` is plural and is used for general admission (`src/main.rs:105-115`). `thread_owner` denotes the engaged **bot** ID, not the human owner (`src/discord/adapter.rs:872-885,1655-1682`). The lane row has no owner-author field. The parent must specify the authoritative human owner identity and bot ownership rule; do not silently equate any allowed/paired author with the owner or let every configured bot reopen the same lane.
3. **Verified-done reopening and cwd lifetime conflict.** Todo 15 accepts replies at `closed|verified_done`, while todo 9 forbids direct reopen from verified_done. `runner::reopen` accepts only closed/failed (`src/lanes/runner.rs:46-83`); `LaneStatus::Working` excludes verified_done (`src/lanes/state.rs:46-69`), and `tests/test_lane_reopen.rs:144-157` explicitly rejects it. Use a serialized verified_done -> closed -> working path, never broaden todo 9's API. If close fails, the required verified_done retention means that path cannot currently reopen. Also, deleting an owned cwd leaves the existing reopen using the now-missing cwd: `runner.rs:441-450` always sets `lane_cwd = initial.cwd`; `cli::start:334-340` only validates it at initial start. The parent must define whether removable worktrees exclude the persistent execution cwd, or how an explicitly owned execution worktree is recreated on reopen. No recreation contract exists in the inspected lane code.

Safe preparation conclusion: do not reuse settlement's worktree selection as deletion permission; do not remove cwd or arbitrary owner worktrees. An explicit persisted creation/ownership record from the producer is required if any paths are to be removed. This is the one justified storage-contract addition, not a speculative lifecycle framework. With no ownership evidence, retain the paths and report the cleanup contract as unresolved rather than claim full close.

## Existing APIs and dependency behavior

### State and reopen (todos 7/9)

- `state::transition(pool, key, to, reason)` uses storage CAS and history (`src/lanes/state.rs:124-174`); normal close allows only verified_done. A reason beginning `forced:` allows working -> closed as well (`state.rs:64-71`). Rejected transitions produce no successful history.
- `runner::reopen(pool, key, text: Option<&str>) -> Result<()>` is a transaction: read closed/failed, CAS to working, reset turns/outcome/claim/evidence/objection, append `reopened` history, delete pending inbox, insert the owner's text or default, commit (`runner.rs:46-83`). It preserves `omo_thread_id`. A second concurrent attempt cannot legitimately append a second reopen once status is working; status CAS alone does not prevent the same Discord delivery later falling through to chat.
- Reopen generation is the maximum `reopened` history ID (`runner.rs:31-43`). Capture and turn-result writes use generation guards. `run_lane` resets error state on generation change (`runner.rs:466-484`), sends the pending reopen message first (`runner.rs:548-555`), and handles `continuity_error` by clearing the stored resume binding and retrying with original brief plus previous-thread-unavailable context (`runner.rs:675-691`). Preserve this behavior rather than duplicate resume logic in the adapter.
- `cli::Reopen` calls that API and `wake(pool)` (`cli.rs:246-253`). `wake` is a Unix datagram hint; the DB is authoritative (`runner.rs:181-219`).

### Current close is only a DB transition

`LaneCommand::Close` (`src/lanes/cli.rs:187-245`) validates force/note symmetry. Ordinary close immediately transitions closed. Forced close writes an allowed sequence of history transitions in one transaction (including done_claimed -> not_done -> working -> closed as needed), then sets closed and wakes the service. It does **not** await cancellation, rename/archive a thread or remove worktrees. This branch must become durable close intent handled by the service; it must not continue declaring `status: closed` before those effects complete. Preserve invalid-input semantics and the current explicit force-note boundary. Do not claim that state::transition alone permits forced close from every state; the CLI currently supplies the intermediate history path.

### Settlement (todo 13)

- `Settler::settle_due() -> Result<Vec<String>>` returns **newly** verified keys, not all verified rows (`src/lanes/settle.rs:34-45,126-132`). The runner exposes it with `with_settlement(clock, signals)` and `settle_due()` (`runner.rs:304-316`). Settlement owns the five-minute deadline and signal checks, not close.
- A transaction reserves `settlement_started`; a restart with that reservation returns not_done instead of replaying arbitrary command signals (`settle.rs:46-95`). The final update is guarded by status, claim_at and reopen generation; rejection creates not_done event and inbox in the same transaction (`settle.rs:96-127`). Do not rerun signals during close or change this reservation policy.
- `worktree_reasons` canonicalizes cwd, probes git, and inspects cwd plus worktrees under cwd or created after lane start (`settle.rs:152-214`). It checks tracked dirt with `--untracked-files=no` and unpushed branches when a remote exists. `include_worktree` uses path containment or creation time (`settle.rs:216-231`); external creation evidence is filesystem birth time or linked registration birth time (`settle.rs:233-274`). This is a verification scope, **not** proof the lane created/owns the path. An unrelated owner worktree created later can match. The main cwd always matches, even though the launcher did not create it.
- Dirty tracked work before verification yields not_done/uncommitted. A race that dirties an explicitly owned worktree after verification must instead produce the todo15 close_failed result while retaining verified_done. Untracked dirt ignored by settlement can still make non-force removal fail; do not weaken git removal to compensate.

### Discord helper (todo 10)

Use the existing `DiscordThreads` methods: `set_status(thread: ChannelId, ThreadStatus) -> Result<String, DiscordThreadError>`, `archive`/`unarchive -> Result<GuildChannel, ...>` (`src/lanes/discord_threads.rs:390-412`). The free functions are at `:250-301`. Errors propagate; archive operations are thread edits, not branch operations. `ThreadStatus::Done`/Working and UTF-8-safe prefix naming already exist.

The runner currently stores `Option<Arc<dyn PostSink>>` (`runner.rs:269-280`), not a lifecycle-capable interface. `PostSink` supports send/edit/set_thread_status, but no archive/unarchive; its status default is a successful empty string (`src/lanes/posts.rs:147-162`). A full-close fake cannot use that default as evidence of archiving. Add the smallest explicit archive/unarchive test seam to the existing transport contract (or a narrowly scoped lifecycle seam if keeping post delivery separate); production must call the actual helper and tests must record/error those operations. No new browser or external control layer is needed.

## Exact integration hooks and file ownership

### Lane service: `src/lanes/runner.rs`

This file should own close execution, cancellation ordering, per-lane serialization and recovery:

1. Extend the existing active task bookkeeping at `serve:361-377` to retain each lane's child cancellation token and completion identity, not only `Arc<Notify>`. Currently only service shutdown directly owns a cancellation root. Notify causes a running turn to cancel on an ineligible status (`runner.rs:625-633`); this is not an awaited full-close API.
2. Replace the logging-only `verified_done_ready(&self, keys)` at `:428-433` with close scheduling after settlement completion (`:387-391`). Schedule outside the socket/select hot path so the service can still receive close/reopen messages and task completions. Prevent duplicate close execution for one lane/generation.
3. Before changing external state or deleting paths, cancel the lane's `run_cancelable` token and observe its task completion. The nested backend turn has a cancellation child and drop guard (`:591-611`). Existing generation guards protect post-reopen writes (`:647-734`); preserve them. Do not abort only the JoinSet task and call that backend cancellation evidence.
4. For ordinary close, re-read verified_done eligibility under the same per-lane serialization as owner reopen. Set Done and archive the stored thread when present; remove only explicitly owned, still-matching registered worktrees with argv `git -C <surviving repository control cwd> worktree remove <owned path>`. Never use `--force`, branch deletion, shell strings or filesystem recursive deletion. The controlling repository must survive removal; blindly running commands from the path being deleted is not a reliable multi-worktree cleanup contract.
5. Commit closed/history only after successful effects and an eligibility/generation check. If non-force removal fails, retain verified_done and durably insert `close_failed` with git stderr and the lead destination. `enqueue_lane_event` exists (`storage/lanes.rs:610-634`); for a failure-state/history/event consistency boundary use the same transaction style as settlement rather than separate unguarded writes. Propagate Discord failures too; they must not result in a false closed receipt.
6. Recover persisted verified_done rows once at service startup, after single-service socket ownership is established (`runner.rs:351-359`), and schedule their close alongside newly verified keys. The current startup list is only working/not_done (`:369`); settler never returns a previously verified row. Record/check partial cleanup so a crash after one removal is not treated as a new failed removal of a missing path, and so an uncertain operation cannot remove a replacement owner path. Repeated startup must not emit duplicate close attempts/events without a persisted attempt boundary. The exact persistent intent/receipt representation must be selected with the ownership contract; no such API exists today.

### Adapter: `src/discord/adapter.rs`

Existing chat dedup is inside `route_claimed_event_with_constituents` (`adapter.rs:1364-1390`), **after** the proposed interception; it cannot protect an earlier lane reopen. Restore Working/unarchive and wake only once the lifecycle state is ready for a new turn. Preserve the unadorned owner message as first prompt: do not prepend channel history/topic context. A failure must stay visible and retain the reply/intent; do not lose it after claiming delivery or route it to chat as recovery. Attachments and `/stop` currently have separate chat behavior (`:1068-1099`); define whether they are lane controls before consuming them as an owner reopen prompt.
