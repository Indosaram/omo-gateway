1. **Headless startup** (`main.rs:646-680`) uses required DATABASE_URL, initializes its real pool, logs PRAGMA database_list, starts only `spawn_lane_service`, and selects lane-task exit/CTRL-C/SIGTERM. Headless must not instantiate these Discord, inbox, cron, readiness/FDA or shared-sink services just to reach the multiplexer.
3. **Lane backend is separate from lead backend** (`lanes/runner.rs:303-338`). LaneRunner uses OmoBackendConfig::lane_from_env, CapturingDispatcher and the same pool, with per-lane generation capture and transcript/activity. Work's newer `OMON_DISCORD_ENABLED=false` guard omits DiscordThreads::from_env. N still unconditionally constructs that sink. Do not port N runner.rs over W. Reusing CapturingDispatcher for lead output is invalid: it rejects non-lane sessions and would feed output into lane activity/generation processing.
4. **Real reply persistence already exists** (`agent/omo_backend.rs:585-654/:1926-1942`). On terminal rendered lead output the backend records a delivery obligation, emits a final Stream action, inserts an assistant row into messages, then updates the obligation. It persists the assistant row even if emission failed, and returns emission failure afterwards. Therefore assistant-row existence alone is not successful turn/delivery proof. Retain terminal backend/actor success and local sink success, as well as the row. Session/thread binding is persisted by the backend and actor; do not write duplicate reply rows in a new sink.
5. **Actor admission is not completion.** N's EventIfIdle sends Ok before inbound persistence/backend execution. EventDispatcher then writes `delivery_reason=lead_turn`. Keep that established contract: admission receipt, not completed reply. Verify completion separately; changing it to completion acknowledgment changes coalescing/rate-limit timing and is not a mechanical port.
6. **Drain is currently a watcher plus ordinary-main shutdown.** DrainWatcher (`drain_control.rs:240-317`) starts with false, has public scan_at, and spawn loops forever without cancellation. Ordinary W main creates it at :962 and handles true by leaving the select and shutting down. N moves creation before mux and attaches the receiver. Merely storing `_drain_handle` does not cancel/join it. Headless needs an initial scan before event admission and a joined watcher lifecycle.
7. **Lead actors are detached tasks** (`multiplexer/router.rs:539-578`). Multiplexer has no shutdown/join API. mark_in_flight_resume_pending (:493) marks tracked sessions; it neither cancels nor joins actors and is not precise proof that each is in flight. Stop is a user-stop operation that sets suspended and is not a service shutdown replacement. Pool.close must happen only after actors finish DB flushes. Adding dispatcher cancellation alone leaves this gap open.

## Contract decisions and tradeoffs

These choices cross existing behavior boundaries; source alone cannot establish the owner's desired semantics. The recommendations below make the unit implementable while exposing the choices rather than silently narrowing acceptance.

### A. What does headless output delivery mean?

Recommended: terminal output is **local transcript delivery**, never external Discord receipt. A private headless adapter consumes Stream frames without external emission because OmoBackend.with_pool already persists terminal assistant output; typing/react are absent (mux dispatcher None), and approval requests fail explicitly rather than waiting for a nonexistent human sink. No fake transport. Emit structured local-delivery log with session key and stream ID, no raw reply/token text. Do not duplicate messages in the adapter.

OmoBackend currently marks the obligation delivered after the adapter returns Ok; document/test that this means local output accepted, not remote Discord delivery. If the same DB is later reopened with Discord enabled, completed headless obligations must not be replayed as unsent Discord messages. Alternative: introduce a distinct local delivery disposition in backend/ledger, which expands owned files and migration/testing scope. If that distinction is required, report/approve that expanded contract before implementation; do not fake Discord delivery or bypass persistence to dodge it.

For emitted media, do not silently claim an external upload. The minimum adapter can reject unsupported external UploadFile/ApprovalRequest actions; required normal lead text uses Stream. If acceptance requires local media capture, define an owned local artifact receipt (not a Discord upload) and add coverage. This is an explicit output contract decision, not omitted lead text behavior.

### B. Reversible drain versus exit-on-marker

Recommended for the new headless path: marker=true gates new System admissions but leaves the runtime alive and lets already accepted lead work complete; marker removal reopens admission. This directly implements the plan's same-event refusal/removal/delivery scenario and uses the same receiver/lifecycle for dispatcher/mux. CTRL-C/SIGTERM/task failure still cancel and join all runtime resources. Existing ordinary Discord path currently exits on marker; preserve that behavior for the minimal port rather than changing production stop semantics silently.

Alternative headless shutdown-on-marker matches ordinary startup but requires marker removal followed by an explicit owned restart before delivery. That can prove persistence/recovery but is not uninterrupted reversible admission. Decide which surface the task14 acceptance promises; do not label restart proof as same-process reversible drain. If ordinary Discord parity requires reversible drain too, expand main's ordinary select deliberately and retest its existing stop contract. Do not turn on Discord to test it.

### C. Recovery of admitted but incomplete System turns

Existing recovery literal sites default to User. Persisted System origin is currently only a `[system]` content marker, not a typed persisted-origin column. Blindly invoking generic auto-resume in headless startup can turn an interrupted System message into User, queue while busy, or cause an already receipted event to vanish from dispatcher eligibility. Minimum headless acceptance can reuse persistent completed sessions/thread bindings and restart **undelivered** lane events without indiscriminate user-session recovery. That does not settle admitted-but-incomplete recovery.

Before promising automatic incomplete-System recovery, choose a durable origin representation/recovery filter, and extend storage/recovery tests. Do not infer typed origin from arbitrary user prose beginning `[system]`, and do not replay old actual8/9 turns. Task14 admission vs completion stays explicit; this recovery guarantee is a remaining contract tradeoff, not reason to shrink the real headless startup/reply/drain unit.
