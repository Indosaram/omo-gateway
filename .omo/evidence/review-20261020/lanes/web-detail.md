D18 FIXED web/src/tracker/detail/descriptionDraft.ts:17-135 + web/src/tracker/detail/Editors.tsx:68-140,166-173,203-211 — the draft rules moved out of the component into `createDraftSaver`, which owns three pieces of state: `draft` (newest text), `lastSaved` (text the server acknowledged) and the module-level `retained` map that outlives the editor. `retained` stores `{ text, owner }`, where `owner` is a monotonically increasing saver id, so an instance that is no longer the newest for an issue cannot write or clear the entry. What each hole the reviewer found now does:

  1. **A failure keeps the newest text, not the text the request carried.** The `catch` calls `retain(draft)` (descriptionDraft.ts:75), never `retain(sending)`. `draft` is updated on every keystroke (line 106) and by `dispose()` (line 120), so text typed while a request was out is what gets kept.
  2. **Retention is synchronous on edit and on unmount.** `edit()` writes the new text straight into `retained` (lines 104-109), and `dispose()` (line 118-121) is called from the unmount cleanup before the flush is started (Editors.tsx:120-126), so text that never reached the network still survives the peek closing. `retain()` drops the entry when the text equals `lastSaved` (line 62), so a clean issue carries no stale entry.
  3. **A stale success cannot delete a newer draft.** After a resolved request the loop sets `lastSaved = sending` and then calls `retain(draft)` (line 84), so the entry is cleared only when nothing newer is pending; if the user typed `Y` while `X` was in flight the loop continues and sends `Y` (lines 69-70) instead of clearing retention.
  7. **A remounted instance owns the entry, not the instance that outlived it.** `createDraftSaver` takes `owner = ++nextOwner` and claims any inherited entry on construction (lines 60-67); `retain()` returns early when `retained` already holds a *newer* owner (lines 73-78), and `sync()` only deletes an entry whose owner is not newer (lines 128-131). So: dispose the old saver with `X` in flight, reopen the same issue (the new saver inherits and claims `X`), type `Y`, then let the old request land - on success the old instance's `retain(X)` would have deleted the entry and lost `Y`, and on failure its `retain(X)` would have replaced `Y` with `X`; with ownership both are refused and `retained` still holds `Y`. A newer instance is never blocked by an older entry (`current.owner > owner`, not `!==`), so it can always reclaim and clear.
  4. **One request at a time, newest text, no false "saved".** `flush()` is single-flight (`inFlight`, lines 90-96) and `state = 'saved'` is only reached once `draft === lastSaved` (line 86), so a slow older response can never mark a newer draft saved.
  5. **The store rollback cannot overwrite the draft.** `sync()` returns early while `draft !== lastSaved` (line 112-113), so the optimistic rollback that `updateIssues` performs on failure does not replace the user's text.
  6. **Failure is visible and retryable.** `state = 'failed'` renders `Not saved` plus a `Retry` button in the tab strip (Editors.tsx:203-211); `finish()` closes the editor only when `flush()` resolved true (Editors.tsx:135-140); the read-only view shows an `Unsaved changes / Retry` row whenever text is pending (Editors.tsx:166-173, `.ld-desc-pending` in detail.css:186-193); and a reopened editor initialises `value` from `retainedDraft` and starts in `'failed'` (Editors.tsx:74-80).

  8. **A remount must not take the optimistic text as the baseline (QA case B/C).** The retained entry persists the acknowledged `baseline` (descriptionDraft.ts:17-26, written at line 90), and a new saver starts from `lastSaved = entry?.baseline ?? initial` (line 78). While a write is pending the store holds the *optimistic* copy of the draft, so `initial` can equal the draft even though the server never took it; using it as the baseline made `dirty()` false, so Retry found nothing to send and `sync()` adopted the rollback. Only `run()` advances the baseline now, from a request that actually resolved — `sync()` never treats the store's optimistic value as an acknowledgement.
  9. **StrictMode's simulated unmount must not fire the owed save (QA case B).** `createUnmountFlush` (descriptionDraft.ts:37-62) defers the owed save by one microtask and cancels it when the effect body runs again; `Editors.tsx:117-136` uses it in the cleanup. React StrictMode mounts, unmounts and remounts every effect in development, so the old cleanup fired a real request while the peek was still open; that request stayed in flight and `flush()` handed its promise back to the user's Retry instead of issuing one, which is exactly the observed `patchCount=0` with the bar never clearing and no toast.
