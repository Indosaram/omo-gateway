### C19: why the first version of this test failed in the gate

`test.log` for revision `5fcfc08` recorded `panicked at src/sessions/watch.rs:481:65: called Result::unwrap() on an Err value: PoolTimedOut`. Line 481 is the shared `pool()` fixture (`SqlitePool::connect("sqlite::memory:")`), not any assertion, so the test died before it exercised `serve`. Cause: the test was `#[tokio::test(start_paused = true)]`. Under paused time tokio auto-advances to the nearest pending timer whenever the runtime has nothing runnable, while sqlx opens and migrates the SQLite connection on its own worker thread rather than on a tokio timer. Virtual time therefore advanced past sqlx's 30 s `acquire_timeout` while the connection was still being established, and the fixture's `unwrap()` panicked with `PoolTimedOut`. Any paused test that touches this pool hits it: the fixture itself must run on the real clock.

Current design, all event-driven and deterministic:

- `#[tokio::test]` on the real clock, so the fixture and every query are unaffected by virtual time.
- `TickSignallingRunner` signals on the local `python3` probe, which is exactly one per tick; `serve` runs a tick's dispatch strictly after the previous tick's `mark_sent` attempt, so a later probe proves the earlier dispatch attempt finished.
- The test awaits the first dispatch, then three tick signals (the buffered first tick plus two complete retry chances) each inside a bounded 5 s `tokio::time::timeout`; a stall fails with a named message instead of hanging.
- `shutdown.cancel()` is the exact stop signal; the test awaits the `JoinHandle` to completion inside a bounded timeout, so once it returns no dispatch can still be in flight and the "exactly once" assertion cannot race.
- The test still fails without the fix: with the trigger blocking the ledger insert, a tick that lacks the in-process fallback re-dispatches the same question, which the final `try_recv` catches.
