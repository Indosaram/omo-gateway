The shipping gate completed with GATE-PASS.

Both decision entry points now claim the proposal with a conditional update as the first statement of their transaction, and only the winner writes the precedent. `UPDATE action_proposals SET state = ? , decided_at = ... WHERE id = ? AND state = 'pending'` (`claim_proposal`, :685) returns whether this answer owns the row. SQLite grants the write lock at that statement, so a competing answer either blocks until the winner commits (then claims nothing) or wins first (then the other claims nothing). A loser records no precedent, bumps no counter and returns the state the winner recorded (`settled_resolution`), so the card press and a short reply for one proposal are one owner decision.

- `finalize_ask_result` (:532) claims first, then reads the row inside the same transaction. Missing row: rollback and `Deny { reason: "proposal #N no longer exists; the action was not run", count_toward_limit: false }`, so nothing is written (`decide_proposal` returns `Err("proposal #N not found")` for the same case). Claim lost: rollback and report the recorded state. Claim won: the precedent write (`write_precedent`, :1243 — the shared body of `upsert_precedent`, now taking a connection) and the row's `precedent_id`/`owner_words` (`finish_decided`) commit together with the claim.
- `decide_proposal` (:914) uses the same claim for `PrecedentScope::Exact`, which is the scope a card press and a short reply share. It deliberately does **not** claim for `PrecedentScope::Class`: a class decision is an explicit owner instruction (`decide ... --scope class`) that may also be recorded after the proposal was already answered, which the existing `todo8` test exercises.
- `record_once_and_check_candidate` (:724) claims before counting, so a replayed once-approval cannot inflate the third-owner-once candidate count.
- `write_precedent` takes `(conn, &PrecedentWrite)`; `PrecedentWrite` (:1212) groups the signature, effect, target scope, decision, scope, origin and owner words, with `PrecedentWrite::of_classification` for the two `finalize_ask_result` sites. The helper therefore has two arguments and needs no suppression: the only `#[allow(clippy::too_many_arguments)]` in the file is the pre-existing one on `upsert_precedent` (`:1184`), whose signature and position are untouched (it appears as unchanged context in the diff), and `effect.rs` carries none, as before.
