# migrate review

### [P1] Gateway is stopped and LaunchAgents disabled before cutover preconditions are checked
- Location: src/migrate/mod.rs:186 (`let gateway = bring_gateway_down(env, &paths.hermes_root, &paths.launch_agents_dir, false)`, followed at :191 by `cutover_cron_stores(..., false)`)
- Trigger: `omon migrate` (non-dry-run, cutover enabled) goes `run_migrate` -> `run_after_config`. Two ordinary inputs make `cutover_cron_stores` fail only after gateway-down has run:
  - `OMON_HERMES_PROFILES` is set and a non-selected profile (including `default`) has jobs. `HermesStoreSynchronizer` only imports selected profiles, but `cutover::discover_stores` walks every profile. Those jobs have no `cron_jobs` row, so they land in `unverified_jobs`. The "refusing to empty" error at src/migrate/cron_cutover.rs:413-421 fires.
  - Any selected job that `HermesJob::validate` rejects is skipped by `sync()`, never imported, and trips the same error.
- Impact: Hermes gateway processes are SIGTERM/SIGKILLed, `gateway.lock` files are deleted, and `ai.hermes.gateway*.plist` files are renamed to `.disabled` with no rollback. The command then exits with an error and no store is emptied, so Hermes is down and its cron jobs are still not migrated. A re-run hits the same error. The dry run reports `would_empty=false` for these stores but does not flag that a real run will fail.
- Fix: before `bring_gateway_down` in `run_after_config`, call `cutover_cron_stores(env, &paths.hermes_root, &pool, true)`. If any store has non-empty `unverified_jobs`, return the step error without touching processes or plists. The real cutover still re-validates under the locks.

### [P1] Cutover verification compares source jobs against DB payloads that contain import-time injected fields, so cutover is refused for stores whose config.yaml sets a timezone or Discord home channel
- Location: src/migrate/cron_cutover.rs:64 (`pub fn normalize_job_payload`, whose ignore-list is used by `canonical_job_payload_matches` at :105)
- Trigger: A Hermes store whose `<home>/config.yaml` has `timezone:` or a Discord `home_channel`/`channel`. `HermesStoreSynchronizer::sync_at` (src/cron/store.rs:1037-1039) sets `job.schedule.timezone` for jobs that have none. `HermesStore::load` (src/cron/store.rs:~930-940) injects `_omon_discord_home_channel` and `_omon_discord_home_thread` into `job.extra`, which is flattened into the payload. Both are persisted in `cron_jobs.payload_json`.
  `cutover_cron_stores` then parses the raw `jobs.json` into a `HermesJob`, which has neither field, and compares it to the DB payload. `normalize_job_payload` ignores only `_omon_hermes_*`, `last_*`, `*_at`, `id` and `repeat.completed`, so the two sides differ.
- Impact: Every job in such a store is classed as "unverified", and `cutover_cron_stores` returns the "payload does not match imported cron_jobs" error. This is reached after gateway-down (see the previous finding), so the migration fails and leaves Hermes stopped. Cutover can never complete for these stores. The fixture in tests/test_migrate.rs has no timezone or home channel in `config.yaml`, so no test covers this.
- Fix: strip the import-injected keys from both sides before comparing. Drop `schedule.timezone` when it equals the store default, and drop `_omon_discord_home_channel` and `_omon_discord_home_thread`. Alternatively, compare the DB payload against a source that has been through the same enrichment as `sync_at`. Fields Hermes mutates at runtime, such as `state` and `enabled` on one-shot jobs completing between import and gateway-down, should also be normalised or handled.

### [P1] Profile-scoped Discord authorization settings override or widen the global allow-list
- Location: src/migrate/config_import.rs:462 (`insert_nonempty(&mut output, key, root_value.or(profile_value));`, with `profile_value` found at :458-461)
- Trigger: `import_config` is called from `run_migrate` / `run_migrate_with`. For each `SCALAR_ENV_KEYS` entry, including `DISCORD_ALLOWED_USERS`, `DISCORD_ALLOWED_CHANNELS`, `DISCORD_ALLOWED_ROLES` and `DISCORD_ALLOW_ALL_USERS`, `root_value.or(profile_value)` falls back to the first profile `.env` that defines the key. `insert_nonempty` uses `BTreeMap::insert`, so it overwrites what the root `config.yaml` section just set via `entry().or_insert_with` (src/migrate/config_import.rs:~405-440).
  - Example 1: the root `config.yaml` has `discord.allowed_users: [111]`, the root `.env` has no such key, and `profiles/work/.env` has `DISCORD_ALLOWED_USERS=222`. The root list is replaced by 222.
  - Example 2: `profiles/work/.env` has `DISCORD_ALLOW_ALL_USERS=true` and the root does not. `true` is written into the gateway `.env`.
- Impact: The migrated `.env` is read globally by the gateway (src/main.rs:105-115). Per-profile bot settings therefore replace the primary owner allow-list or open the bot to all users. This is an authorization widening or misconfiguration. The `.env` backup exists but is not applied automatically.
- Fix: do not fall back to profile values for the access-control keys (`DISCORD_ALLOWED_*`, `DISCORD_ALLOW_ALL_USERS`, `DISCORD_IGNORED_CHANNELS`, `DISCORD_FREE_RESPONSE_CHANNELS`, `DISCORD_HOME_CHANNEL`). Use root-only values for these keys, with root `.env` taking precedence over root YAML. If merging is wanted, union the lists and never import `ALLOW_ALL` from a profile.
